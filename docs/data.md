# MIMII dataset: source, download and verified properties

Everything below was checked on the actual Zenodo record and files. Numbers
are regenerated by the commands given in each section.

## Source

- Purohit et al., "MIMII Dataset: Sound Dataset for Malfunctioning Industrial
  Machine Investigation and Inspection", DCASE Workshop 2019 (arXiv:1909.09347).
- Zenodo record [3384388](https://zenodo.org/records/3384388),
  DOI 10.5281/zenodo.3384388, version "public 1.0", published 2019-09-20.
- License: CC BY-SA 4.0 (Zenodo metadata).

## Archives

The record holds 12 ZIP archives, one per (SNR, machine type), 100.24 GB in total
(100,243,834,344 bytes). Names, sizes and MD5 digests come from the Zenodo API
(2026-09-29) and are committed in
[`noisemismatch/data/mimii_zenodo_3384388.csv`](../noisemismatch/data/mimii_zenodo_3384388.csv).

| SNR | fan | pump | slider | valve |
|---|---|---|---|---|
| −6 dB | 10.88 GB | 8.24 GB | 7.95 GB | 8.04 GB |
| 0 dB | 10.41 GB | 7.87 GB | 7.51 GB | 7.49 GB |
| +6 dB | 10.16 GB | 7.66 GB | 7.13 GB | 6.92 GB |

## Download and verification

```bash
python -m noisemismatch.data.download --check-manifest  # manifest == live record?
python -m noisemismatch.data.download                   # download + MD5 check
```

Archives are written to `<data_root>/downloads/`, logs to `<data_root>/logs/`, and
the per-archive verification report to `<data_root>/downloads/verification.json`.
aria2c checks each MD5 after download; the script then recomputes every MD5
independently with Python's hashlib.

## Files

All tables below are regenerated by `python scripts/make_data_tables.py` into
[`data_tables.md`](data_tables.md); this section only quotes them.

- Each archive holds members `<machine_type>/<machine_id>/<label>/<clip>.wav`
  (e.g. `pump/id_00/abnormal/00000000.wav`), `label` ∈ {normal, abnormal}. The
  SNR is only encoded in the archive name. WAV members are deflate-compressed;
  they are read directly from the verified archives (no extraction).
- 54,057 WAV files: 18,019 per SNR (14,719 normal, 3,300 anomalous), four machine
  IDs per type (`id_00`, `id_02`, `id_04`, `id_06`). Per-ID counts equal those of
  Table 1 of the MIMII paper for these IDs.
- Every file: WAVE_FORMAT_EXTENSIBLE, 16-bit PCM, 8 channels, 16 kHz, 160,000
  frames (10.000 s), 2,560,080 bytes (80-byte header). Header fields were parsed
  for all files and cross-checked with soundfile on a random sample.
- Every clip name exists at the three SNRs.

## File names do not identify recordings across SNRs

MIMII builds its SNR versions by mixing each machine recording with factory noise
(paper, Sec. 3). Comparing waveforms shows that **the file of a given name at
−6 dB is often not the recording of the file of that name at 0 or +6 dB**:

| SNR pair | normal clips, same name = same recording | anomalous clips |
|---|---|---|
| 0 ↔ +6 dB | 99.9 % | 99.8 % |
| 0 ↔ −6 dB | 89.3 % | 57.1 % |

(accepted content matches, see below; exact counts in `data_tables.md`).

- **A permutation, not a time shift.** Example, pump `id_00` anomalous: the −6 dB
  file `00000000` holds the recording of the 0 dB file `00000051` (correlation
  0.61 on channel 0; best other candidate 0.03), `00000001` holds `00000000`
  (0.77), `00000002` holds `00000050`. The matched indices interleave two
  sequences (51, 0, 50, 1, 58, 2, 59, 3, …), which suggests a different
  enumeration order when the −6 dB files were generated. For same-name files,
  the maximum cross-correlation over all lags is about 0.03–0.04: no shift
  explains the mismatch.
- **Scope.** At −6 dB, no accepted match crosses a machine-ID or label folder:
  names are permuted within `<machine_id>/<label>/`. At +6 dB, 9 accepted
  matches cross a folder boundary (8 involve valve `id_00` anomalous clips);
  none of these identities is kept.
- **Consequence.** A split on file names would let a test recording be used for
  training at another SNR. Clip identities are therefore defined by content.
- This inconsistency is not mentioned in the MIMII paper, and no issue about it
  exists in the baseline repository (checked 2026-09-29).

## Content-based clip identity

The rule is defined in [`protocol.md`](protocol.md) ("Clip identity") and was
fixed before any exclusion count was computed. In short: each 0 dB file is a
candidate identity; the score of two files is the lag-0 Pearson correlation of
their waveforms averaged over the 8 channels; each 0 dB file is compared with
every file of its machine type at +6 dB, then (reference = its 0 dB and +6 dB
versions) at −6 dB; a match is accepted if it is part of the optimal one-to-one
assignment, a mutual best match, scores ≥ 0.10 with a margin ≥ 0.05 over every
competitor, and, at −6 dB, both reference versions support it (≥ 0.05). An
identity is kept only if matched at both +6 and −6 dB.

```bash
CUDA_VISIBLE_DEVICES=0 python -m noisemismatch.data.matching  # score matrices (~40 min, ~47 GB RAM)
python -m noisemismatch.data.identity                          # metadata/mimii_identity.csv
python scripts/make_data_tables.py                             # docs/data_tables.md
```

**Validation.** Between 0 and +6 dB, taking the same-name file as ground truth,
the rule has a precision of 99.93 % and a recall of 97.16 % over the 18,019
clips; per group, precision is ≥ 99.3 % except for valve `id_00` anomalous clips
(94.5 %). At −6 dB, for 93.9 % of accepted matches the two score terms, computed
from independently noised versions, each select the same −6 dB file.

**Kept identities.** 15,180 of 18,019 clips (84.2 %). Exclusions are concentrated
where matching is hardest: quiet or impulsive clips, and slider `id_00` normal
clips (50 % excluded). **No anomalous clip of valve `id_00` is kept**: these clips
are dominated by noise even at +6 dB (median score 0.15 against 0.5–0.8
elsewhere), so their identity cannot be established.

**Sign test of the accepted matches.** Correlations between distinct recordings
of tonal machine sounds are coincidences of random relative phase, hence
sign-symmetric, whereas the correlation of two versions of one recording is
positive. If an accepted match were such a coincidence, it would be exceeded (in
absolute value) by the most negative non-match of its row with probability 1/2.
**No exceedance occurs**: 0 of 15,180 accepted matches at −6 dB and 0 of 17,521 at
+6 dB. Per group (machine type × ID × label, 81 to 1,016 matches, valve `id_00`
excluded), the one-sided binomial p-value is at most 4 × 10⁻²⁵. Calibrating the
exceedance probability on each row's best non-match instead of 1/2 (observed
rates 0.6–45 %) gives p ≤ 2.4 × 10⁻³ in every group. Per-group figures are in
[`data_tables.md`](data_tables.md) ("Accepted matches vs non-matches").

This test rules out sign-symmetric coincidences only. Coincidences caused by a
reused noise segment are positive; they are ruled out at −6 dB by requiring the
match to be supported by both the 0 dB and the +6 dB versions, which carry
independent noise segments. At −6 dB, in 289 of the 15,180 accepted rows (1.9 %),
the best non-match would itself pass the row-wise thresholds; the accepted match
exceeds it by at least the 0.05 margin in each case.

A group-level view (share of rows holding a non-match ≤ −(median accepted
score)) flags fan `id_00` anomalous clips (81 of 357 rows at −6 dB): their tonal
sounds give heavy, symmetric tails. Decisions are taken per row, and every row of
that group passes the sign test; the group is kept (protocol, Amendment 2), and
results are also reported without fan `id_00`. For 28 identities, the accepted
score is below the 99.9th percentile of |score| over the non-matches of their
group (pump `id_06` normal: 14 + 1 at +6 dB; slider `id_02`: 12; fan `id_00`
anomalous: 1); they belong to the strict evaluation variant.

## Other observed properties

- **Noise differs between the SNR versions of a recording.** For the kept
  identities, the −6 dB version is far from the span of the 0 and +6 dB versions:
  the relative residual of regressing it on them is 0.88–0.94 (median per machine
  type; minimum 0.44), estimated from the channel-averaged correlations. If one
  noise segment had been rescaled for the three SNRs, it would be close to 0. Each
  SNR version was therefore mixed with a different noise segment.
- **Noise segments are reused across files and machine types.** On channel 0,
  about 20 % of the −6 dB files correlate better with a 0 dB file of *another*
  machine type than with any file of their own (up to 0.91), against at most
  4.5 % at +6 dB: the factory-noise pool is shared.
- **High correlations between distinct files at +6 dB are phase coincidences.**
  Pairs of distinct files of one machine ID with a +6 dB score ≥ 0.5 exist in fan
  (146), pump (141) and slider (131), but pairs with a score ≤ −0.5 are about as
  frequent (144, 107 and 103), and the same symmetry holds at ±0.3 and ±0.2.
  Shared recordings or shared noise can only produce positive correlations; a
  symmetric distribution is what two independent recordings of a tonal or
  periodic machine sound give at lag 0 (random relative phase). These pairs are
  therefore **not** shared recordings. (An earlier version of this document,
  and the rationale of the cluster split, interpreted them as shared machine
  sound because their score rises with the SNR; that rise is expected for any
  machine-driven correlation, coincidental or not, and does not discriminate.)
- **Shared noise is visible at −6 and 0 dB.** There, high scores between distinct
  files are almost only positive (e.g. pump, −6 dB: 38 pairs ≥ 0.5, none ≤ −0.5),
  as expected from reused noise segments.

## Consequences for the study

- **valve `id_00` is removed** from all analyses (training and test, every model,
  auxiliary ID classes included): none of its anomalous clips can be identified
  across SNRs. The study covers 15 machine IDs (protocol, "Data").
- **fan `id_00` is kept**; a robustness aggregation without it is reported.
- **slider `id_00` has only 178 normal training clips** (534 kept normal clips,
  356 of them needed in the test set to match its 356 anomalous clips), against
  301 to 801 for the other machine IDs. It is kept; results for this ID rely on a
  small training set. The MIMII release has 1,068 normal clips for this ID, as
  for `id_02`: the small training set and the resulting class imbalance come from
  the identity exclusions (protocol, "Known limitations").

## Splits

```bash
python -m noisemismatch.data.build_split          # candidate splits and checks
python -m noisemismatch.data.build_split --save   # write (never overwrites)
```

- **Main split** (`metadata/mimii_split.csv`): the 14,360 kept identities of the 15
  machine IDs, drawn per identity with the MIMII protocol (every anomalous clip
  and as many normal clips in the test set; seed 12345); 8,778 training and 5,582
  test identities (2,791 anomalous), exactly balanced in every machine ID.
- **Sensitivity split** (`metadata/mimii_split_sensitivity.csv`, 2×2 experiment at
  0 and +6 dB): the 16,507 identities matched at +6 dB, same procedure; 10,301
  training and 6,206 test identities.
- **Leakage**: automated tests check, through the identity table, that each kept
  identity has one file per SNR, that no file serves two identities, that no
  recording is both in a training and a test set at any SNR, and that the saved
  splits are reproduced from the identity table and the seed.
- **Noise reuse** (protocol, "Noise reuse check"): the share of test files that
  share a noise segment (same-SNR score ≥ 0.5) with a training file of the same
  machine ID is at most 2.2 % (same machine type: 3.4 %), and differs between
  normal and anomalous test files by at most 2.2 points. The largest difference,
  at +6 dB (2.2 % of normal against 0 % of anomalous files), comes
  from sign-symmetric tonal coincidences, not from noise. Figures in
  [`data_tables.md`](data_tables.md).

## Noise reuse across machine types

Wilkinghoff and OS-SCL are trained on all machine types, so a noise segment
shared by a test file and a training file of another machine type would be a
shortcut for these two models only. Measured on the saved splits with the
criterion of the intra-type check (same-SNR score ≥ 0.5, 8-channel score of
`noisemismatch.data.matching`; `python -m noisemismatch.data.cross_noise`,
`metadata/mimii_noise_check_cross_type.csv`):

| Split, SNR | other types: normal / anomalous | all types: normal / anomalous |
|---|---|---|
| main, −6 dB | 9.5 % / 9.2 % | 12.7 % / 12.3 % |
| main, 0 dB | 5.5 % / 3.4 % | 7.1 % / 4.6 % |
| main, +6 dB | 0 % / 0 % | 2.2 % / 0 % |
| 2×2, 0 dB | 7.3 % / 5.1 % | 9.2 % / 6.9 % |
| 2×2, +6 dB | 0 % / 0.03 % | 1.8 % / 0.03 % |

- Cross-type noise sharing is real (no score ≤ −0.5 against other types: the
  high scores are positive-only) and frequent at −6 dB, where noise dominates, but
  balanced between normal and anomalous test files.
- The largest normal/anomalous difference is 2.5 points (main split, 0 dB, all
  types; 2.1 points against other types only), below the 5-point limit of the
  protocol. Normal test files share noise with training files slightly more often
  than anomalous ones at 0 dB; this is reported as a caveat for the two
  cross-type models.
- The +6 dB "all types" shares are the within-type tonal coincidences described
  above: 61 normal test files have a training partner scoring ≥ 0.5 and 47 have
  one scoring ≤ −0.5, a sign-symmetric pattern that shared noise cannot produce.

## Relation to DCASE 2020 Task 2

The MIMII part of the DCASE 2020 Challenge Task 2 development dataset (Zenodo
3678171) — fan, pump, slider, valve — **corresponds to channel 0 of the MIMII
recordings at −6 dB**, under other file names. DCASE 2020 Task 2 also contains
ToyCar and ToyConveyor (from ToyADMOS), which this section does not concern; the
dataset as a whole is not MIMII at −6 dB. The official sources (task web page,
task description paper, Zenodo record) document no SNR for this part. Checked on 2026-09-30 without downloading that dataset (HTTP range
requests on its ZIP archives, 3.3 MB in total):

- its archives list exactly the MIMII files of machine IDs 00, 02, 04 and 06
  (e.g. valve: 4,170 files; per ID, all anomalous clips and 100 normal clips in
  `test/`, the other normal clips in `train/`);
- seven files (one or more per machine type) are bit-identical to channel 0 of a
  MIMII −6 dB file (e.g. DCASE `valve/test/normal_id_02_00000000.wav` = MIMII
  −6 dB `valve/id_02/normal/00000638.wav`), and not to any 0 or +6 dB file;
- rewriting a MIMII −6 dB channel 0 as a mono 16-bit WAV (44-byte header)
  reproduces the DCASE file byte for byte, so the CRC-32 values listed in the
  DCASE archives identify every file;
- full mapping (`python -m noisemismatch.data.dcase2020`,
  `metadata/dcase2020_mimii_mapping.csv`): all 18,019 MIMII −6 dB files (fan
  5,550, pump 4,205, slider 4,094, valve 4,170) match exactly one of the 18,019
  DCASE files by CRC-32, one to one (18,019 distinct CRC-32 values), with the same
  machine ID and label (DCASE `anomaly` = MIMII `abnormal`) in every row; DCASE
  places 13,119 normal clips in `train/`, and 1,600 normal and 3,300 anomalous
  clips in `test/`.
- no DCASE file corresponds to the 0 or +6 dB versions: none of the 36,038 MIMII
  files at those SNRs, rebuilt the same way, has the CRC-32 of a DCASE file
  (`python -m noisemismatch.data.dcase2020 --other-snrs`,
  `metadata/dcase2020_other_snrs_check.csv`).

**What is redistributed.** No audio content of the DCASE 2020 development set
(CC BY-NC-SA 4.0) is redistributed: `metadata/dcase2020_mimii_mapping.csv` and
`metadata/dcase2020_other_snrs_check.csv` contain only file names and CRC-32
checksums, from which no audio file can be reconstructed. They make the finding
verifiable: a reader can recompute the CRC-32 of the rebuilt MIMII files and
compare them with the central directories of the DCASE archives.

Consequently, results published on the DCASE 2020 development set for fan,
pump, slider and valve are results on channel 0 of the MIMII recordings at −6 dB
(results for ToyCar and ToyConveyor are not), and the file mapping and split of
these four machine types can be rebuilt from the MIMII archives. The DCASE 2020 evaluation set (IDs
01, 03, 05) is not part of the public MIMII release. The DCASE 2022 development set
(MIMII DG, ToyADMOS2) consists of other recordings.
